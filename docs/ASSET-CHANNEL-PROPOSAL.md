# 资产通道生命周期与兼容建议（提案，未实施）

建议先让大图摆脱重复Base64/JSON传输，同时保留现有schema2可编辑项目。先做可撤回的运行期通道验证，不把它与新的持久化格式绑定。本轮没有添加资产接口、目录映射、schema3、迁移或新增权限。

## 现状

`NativeImages`及编辑器边界传递PNG data URL。恢复存储已将原图按SHA256分离，校验20MiB图像/4MiB元数据，使用不可覆盖文件、同目录临时写入及SQLite索引；加载会重建现有项目。这里已有的持久化能力应复用，不另造第二份恢复库。WebView2只映射打包web目录，并检查导航、消息和资源来源；用户恢复目录不能直接作为网站目录映射。

## 生命周期建议

| 所有者 | 建议的引用与释放规则 |
|---|---|
| 当前文档与历史 | 图像不可变，内部引用同一资产ID；持有当前文档和可撤销历史的强引用，视图卸载/工作台切换不释放仍被历史引用的图像 |
| 渲染、导出、OCR | 每项操作获取有界读租约，携带文档ID/修订/代数；完成或取消后释放，迟到结果丢弃。取消请求不等于提前关闭仍在读取的流 |
| 内存缓存 | 原始PNG与解码缓存分开计量；只回收没有文档/操作引用的条目。超额先拒绝新操作或显式提示，不能静默丢弃未保存编辑 |
| 恢复持久化 | 沿用内容哈希、原子写入与数据库引用；运行期租约与持久化引用分开，清理不能删除活跃读者或其他用户文件 |
| 退出/崩溃 | 内存租约随进程结束；临时文件仅清理专属命名空间。重启通过恢复索引校验，不重放运行期URL，不依赖TTL保证正确性 |

原图、遮盖后的OCR派生图、导出结果使用不同资产身份。派生图只在明确处理操作中短暂存在，不覆盖原图，也不绕过现有遮盖处理。资产ID、路径、图片及识别文字不进入普通日志；UI应继续说明可编辑项目包含原图。

首个验证阶段建议保持现有图像尺寸/体积限制，不因更换传输方式自动扩大支持上限。去掉Base64不等于零复制，WebView解码、画布和GPU仍占内存；必须测量宿主与WebView进程，不能只报告托管分配量。

## 传输选项与验证门槛

建议优先验证窄化的`WebResourceRequested`图像响应：不透明资产ID、限定方法/资源种类、PNG内容类型、受控流和清理。它能提供动态资源，但事件经过宿主UI线程，需避免在该线程解码或进行大图同步I/O，并明确异步读取结束前的流生命周期。[Microsoft本地内容文档](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/working-with-local-content)列出了虚拟主机静态映射和动态响应的不同成本，不能先假定某一种一定更快。

必须先验证它与当前虚拟主机映射的路由是否冲突；如需专用资源origin，消息桥仍只信任编辑器origin，资源origin只返回图像，不赋予原生桥能力。不扩大通配网络或文件访问。消息及来源继续逐次验证，符合[Microsoft WebView2安全指引](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/security)。

跨origin图像还会影响Canvas可导出性，需明确响应CORS与图像加载属性，不能用放宽浏览器安全参数绕过。[MDN Canvas跨域图像说明](https://developer.mozilla.org/en-US/docs/Web/HTML/How_to/CORS_enabled_image)解释了该限制。上述路由/流/CORS是实施前的技术验证项，本轮没有宣称已在真实WebView2中通过。

备选的专属只读临时目录映射更简单，但会产生图像落盘、额外文件复制及崩溃清理问题；在用户确认是否允许临时落盘和保留期限前，不选为默认。直接映射恢复库、暴露任意路径、以可编辑项目里的任意URL读取文件，均不建议。

## 项目兼容建议

1. 运行期URL/租约不写入项目。新运行时继续读v1/v2，内部转为资产引用；保存时仍以现有schema2自包含PNG导出，保留原图字节和全部编辑字段。
2. 保留现有导入/保存大小上限与清晰错误。新通道不能让用户编辑一个旧格式无法保存的项目后才发现不可移植；若以后扩限，要同时决定兼容导出或新格式的边界。
3. ZIP容器、旁置资产或schema3只列为后续独立提案。若选择新格式，采用显式“另存为”、保留旧文件、清楚标识旧版本不兼容，并准备双向测试；不进行不可逆就地升级或自动批量重写。
4. 恢复库与项目文件分开演进；若以后需库版本变更，先做备份、并排验证和回退方案，再获相应迁移决定。
